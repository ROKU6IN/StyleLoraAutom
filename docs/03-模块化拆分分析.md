# 03 模块化拆分分析（历史讨论稿）

0.52.0 更新：用户已确认采用本节预留的 NovelAI 直连路线，新增 `NaiDirectBackend` 并接入现有来源闭环，无需 Launcher。下述原建议保留用于追溯；当前合同见 [直连实现与验收](59-F02-NovelAI直连实现与验收.md)。

## a. 是否要做成本地特化 agent？生图功能放哪里？

**结论：要做，但 agent 只是外壳。核心是一个确定性的 Python 流水线服务，agent 通过它的工具做判断。生图继续依赖 Launcher，只在我们这边加一层可替换的适配器。**

为什么要 agent：流水线里有四类判断工作（提示词设计、边界样本裁决、tag 冲突、统计解读）离不开 LLM，而且各阶段之间要根据统计结果回跳（覆盖度不够 → 回 S1 补数据）。这种「看结果再决定下一步」用 agent 编排比写死状态机灵活。

为什么 agent 不能是核心：批量搬运、去重、导出这些要求幂等、可重跑、可单测，放进 LLM 循环里既贵又不稳定。所以 agent 坏了或换模型，流水线本身照样能用 CLI 跑完。

生图放哪里：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **依赖 Launcher（推荐）** | 0 Anlas 判断、审批、账号管理、tag 库、反推、画廊都现成；实测提示词不会被冲掉 | 必须开着 GUI；model/sampler 只能改页面设置；版本升级可能改 schema |
| 自己集成 NAI API | 无 GUI 依赖、参数完全可控、可无人值守 | 要自己处理鉴权、计费判断、V4/V5 请求格式、元数据；Launcher 的扣费保护全没了，误操作直接花钱 |

做法：定义 `ImageBackend` 接口（`probe / prepare / submit / fetch`），先实现 `LauncherMcpBackend`。直连 NAI 的 `NaiDirectBackend` 只预留接口不实现，等真的遇到 Launcher 不可控再做。后续 ComfyUI 本地生图（角色 LoRA 可能需要）也走这个接口。

## b. 是否需要专用前端？技术路线？

**结论：需要，但第一版只做「审图 + 看板」，不做全功能控制台。**

必要性来自一件 CLI 和聊天界面都做不好的事：**人工审图**。几百张图要快速过一遍、批量 reject、看 tag 对照、改 caption，这是整个流程里人花时间最多的地方。其他环节（启动 run、看统计）CLI + agent 对话够用。

技术路线建议：

| 选项 | 评价 |
|---|---|
| **FastAPI 后端 + React + Vite + TypeScript SPA，本地 `127.0.0.1` 访问（已采纳）** | 后端和流水线同为 Python，直接共用 manifest 层；浏览器做图片网格、虚拟滚动、快捷键最省事；生态最厚（TanStack Virtual/Query、shadcn/ui），subagent 写 React 质量更稳；以后要打包成桌面应用再套 Tauri，前端代码不用改 |
| Svelte / SvelteKit（已否决） | 写起来更干净、代码量更少，但虚拟滚动与组件库选择少；Svelte 4/5 语法差异大，subagent 容易混用过时写法 |
| Gradio / Streamlit（已否决） | 起步最快，但交互模型是整页重算，做不了虚拟滚动、框选多选、键盘流式审图，后期会推倒重来。可作为内部调试页 |
| Flutter（与 Launcher 同栈，已否决） | 风格统一，但后端是 Python，多一层通信；Flutter Web 调试体验差。只有要做移动端审图才值得 |
| Tauri / Electron | 不是前端框架，是桌面外壳，里面照样跑 React。第一版不需要，等需要托盘/拖拽/自启动时再套 |

前端只读写 manifest（经 FastAPI），不直接调 Launcher。安全上：只绑 127.0.0.1；即使本地，也加一个启动时生成的随机 token，防止浏览器里其他网页跨站调本地接口。

视觉层为后续美术精加工预留：设计令牌（基础色阶 + 语义层）、`data-theme` 主题切换、业务组件与视觉包装分离（`ui/` 层）、图标与空状态走可替换槽位、动效集中定义并遵守 `prefers-reduced-motion`。详见 `.opencode/agents/frontend.md`。
## c. 为角色 LoRA 数据集和训练集成做的预留

两条路线的差异：

| | 画风 LoRA | 角色 LoRA |
|---|---|---|
| 起点 | 画风 tag 串 + 覆盖矩阵 | 角色参考三视图（少量种子图） |
| 生成方式 | txt2img 批量 | 参考图驱动：NAI 4.5 precise reference / vibe、img2img、LLM 改写增图 |
| 要保持一致的 | 画风 | 角色身份（发型、瞳色、服装特征） |
| 要多样化的 | 内容 | 姿势、视角、表情、场景、**画风**（防止画风绑进角色） |
| caption 规则 | 剔除画风 tag，触发词承载画风 | 剔除角色固有特征 tag，触发词承载角色；保留可变服装/动作 |
| QC 重点 | 画风一致性、画面缺陷 | 身份一致性（与参考图的相似度） |

需要做的架构化：

1. **「数据集类型」作为一等概念**。`runs` 表加 `dataset_kind`（style / character / ...），每种类型对应一个 profile（插件）提供：提示词策略、生成策略、QC 规则、caption 规则、blocklist 来源。流水线骨架（S0–S6、状态机、manifest）共用，profile 只替换各阶段的策略实现。
2. **manifest 支持图片之间的血缘**。加 `parent_id`、`source_kind`（txt2img / img2img / reference / inpaint / external），以及 `references` 关联表（一条记录用了哪些参考图、强度）。角色路线的「三视图 → 增图 → 再增图」靠这个追溯。
3. **资产库独立于 run**。参考图、三视图、vibe 编码、角色设定卡（固有特征 tag 列表）放进 `assets` 表，多个 run 复用。对应 Launcher 的 precise reference / vibe 库，但以我们这边为准，同步过去。
4. **生成请求是通用结构**。`GenerationRequest` 从一开始就带可选的 `source_image`、`references[]`、`characters[]`、`strength`，画风路线只是不填。`ImageBackend` 接口不需要以后再改。
5. **QC 规则可插拔**。QC 写成「检查器列表」，每个检查器产出分数 + 理由。角色路线以后加「与参考图的特征相似度」检查器，不影响画风路线。
6. **人工节点是一种通用状态**。`needs_review` + 审图前端，角色路线的「这张还像不像本人」判断复用同一个界面。
7. **训练集成预留**：
   - 导出层定义 `Exporter` 接口，第一版输出「图片 + 同名 txt」，后续加 kohya / sd-scripts / diffusion-pipe 等目录格式和 toml 配置生成。
   - 新增 `train_jobs` 表（数据集版本、训练配置、产出 LoRA 路径、状态），训练器作为另一个 backend（`TrainerBackend`：`prepare / launch / poll / collect`），本地子进程起步。
   - 评估回流：`eval_runs` 表记录 LoRA 出图结果，失败案例可以反查到数据集版本和具体记录，驱动下一轮定向补数据。
   - 调度：所有长任务（生图批、打标、训练）统一走一个本地任务队列（SQLite 持久化的 job 表即可，第一版不引入 Celery/Redis），前端和 agent 都只看 job 状态。

第一版只落地 1、2、4、7 的数据结构（表和接口），不实现角色和训练逻辑。

## d. 原始提示词：数据库还是 LLM 生成？

**结论：混合。数据库提供「合法且真实的 tag 组合」，LLM 负责「按矩阵挑选和组合」，最终由确定性校验把关。不建议纯 LLM 生成。**

纯 LLM 的问题：会编造不存在的 tag、偏好高频套路（构图单一）、下划线/别名不规范、难以精确控制分布。纯数据库随机拼接的问题：组合不自然、语义冲突（`sitting` + `running`）。

可用的现成数据源：

| 来源 | 内容 | 获取方式 | 用途 |
|---|---|---|---|
| Launcher 内置 Danbooru tag 库 | tag、别名、热度、中文翻译、共现包（suggest 模式需要） | MCP `search_tags` | **合法性校验、别名归一**（首选，零额外依赖） |
| Danbooru 公开 tag 数据集 | tag 全表 + 分类（general/character/copyright/artist/meta）+ post_count | HuggingFace 上有多个公开导出 `[待确认具体数据集与许可]` | 本地离线 tag 分类表，用于构建 blocklist（画师类、风格类自动识别） |
| Danbooru 帖子 tag 组合 | 真实图片的完整 tag 串 | Launcher `browse/search_online_gallery`，或公开的 Danbooru 元数据导出 | **内容段采样池**：真实组合天然自洽 |
| 用户自己的 Launcher 词库 / 随机词库 | 用户积累的分类词条 | MCP `list_tag_library_*` | 补充采样池 |

推荐流程：

1. **矩阵定义**（人定）：维度如「人数 × 构图 × 场景 × 动作类别 × 时间光照」，每格目标数量。
2. **候选采样**（确定性）：从真实帖子 tag 串里按矩阵格子过滤 → 剔除画师/风格/版权（受控比例）/meta tag → 得到内容段候选。
3. **LLM 精修**（批量，结构化 JSON 输出）：对每格给 N 条候选，LLM 去冲突、补缺失维度、控制长度，不允许引入新 tag 以外的自由文本。
4. **确定性校验**：每个 tag 过 `search_tags`/本地表；不存在的删掉或映射到别名；查画风 blocklist；按语义（tag 集合 Jaccard）去重。
5. 入库 `prompt_plans` / `records`。

LLM 侧需要准备：

- **一个 prompt-designer skill**（`.opencode/skills/prompt-designer/SKILL.md`）：Danbooru tag 书写规范、NAI V4.5/V5 提示词结构（base caption + 角色段、权重语法 `1.2::tag::`）、禁止项（画风词、画师名、质量词由系统追加）、输出 JSON schema、正反例。
- **输出 schema 校验**：LLM 输出不合 schema 直接重试，最多 2 次，仍失败该格标记失败。
- **调度**：由流水线代码直接调 LLM API（不经过 opencode agent），按格子分批，每批 20–50 条，并发受控。用便宜模型（deepseekv41f / gpt61luna）。opencode agent 只在「矩阵设计」「统计结果不理想该怎么补」这种低频高价值节点介入。
- **模型路由配置**：`config/llm.yaml` 定义角色 → 模型映射（prompt_designer、vision_reviewer、caption_writer），和开发用的 opencode agent 配置分开。

开放问题：视觉复核和自然语言 caption 需要多模态模型，当前 8 个端点哪些支持图像输入还没测，这会决定 S4/S5 能否用 API 实现，还是要本地跑 VLM（如 Qwen-VL 系列）`[待测]`。
