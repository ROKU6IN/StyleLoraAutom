# F12 第四阶段：GPU 与动态批处理验收

版本 0.12.0，2026-10-25。实现 F12 §5 的真实 CUDA 执行、显存档案、动态 batch、OOM 缩批与 CPU 回退，并将多图计算接入既有持久任务。全部本地开发，没有初始化 Git、提交、推送或发布安装包。复用已安装的固定 WD 权重和本地参考样例，未上传图片、调用 NAI 或 LLM。

## 实现范围

- `tagging/model_runtime.py`：支持 GPU 可选安装档，按 ORT 官方接口从 NVIDIA Python 包加载 DLL。CPU/GPU 分发包互斥。CUDA 使用设备 0、float32、关闭 TF32、`kSameAsRequested` 分配策略、单线程主机调度和原有 ORT_DISABLE_ALL；加载后核对 CUDA provider 与张量合同，禁止 ORT 隐式会话回退。
- `tagging/gpu_profiles.py`：开发审核的显存档案，绑定 manifest 摘要、ORT、CUDA/cuDNN/cuBLAS 版本、GPU 名称/总量、驱动和会话策略。HTTP 不提供档案导入或信任摘要入口，验收报告也不自动写成生产档案。
- `tagging/device.py`：NVML 优先，失败时用有超时的固定位置 nvidia-smi；读取身份用于匹配档案。遥测仅在内存，硬件存在或 provider 已注册都不等于模型会话成功。
- `tagging/predictor.py`：有匹配档案且模型为 dynamic batch 时，按用户上限和空闲显存合批，最多 4 图；CPU、固定 batch=1、无档案均逐图。每批保留 max(1 GiB, 总显存 20%)，已知档案连一图也容不下时回退 CPU。OOM 减半到 1 后只对同一模型作一次 CPU 尝试；CPU 仍失败记图级错误。解码失败/非法概率逐图隔离，不把一图错误扩散成其它图片的成功结果。
- `services/jobs.py`：冻结范围内按批计算，每图继续独立校验 SHA/文件身份、WD current 引用及事务提交。暂停完成当前接受批次，不再取下一批；取消丢弃未提交结果；库忙保留整个未提交结果队列，恢复不重做成功计算。新快照 `wd-runner-v2`；历史 `wd-runner-v1` 保持单图在途单位。
- 缓存保留“实际 provider”区分，CUDA 增加会话策略版本。批大小、显存瞬时量和 OOM 重试次数不进入结果键；旧 CUDA 策略结果不会误命中新策略，CPU 键保持兼容。
- 前端新增批大小上限 1/2/4，CPU 模式固定 1；模型页显示匹配本机的 CUDA 档案数量，任务详情显示冻结上限。能力响应增加 `max_batch_size`、`cpu_batch_size`、`cuda_profiles`，不再用固定 `actual_batch_size=1` 描述所有任务。每图实际设备/批大小仍记录于标注 params。

## 真实环境、数值和显存依据

本机 NVIDIA GeForce RTX 5060 Ti，总显存 17,103,323,136 字节，驱动 610.88。项目新增独立 `.venv-gpu`，原 `.venv` 的 CPU 环境保留。GPU 环境：Python 3.12、Pillow 12.3.0、onnxruntime-gpu 1.31.0、CUDA Runtime 13.4.92、cuDNN 9.27.0.42、cuBLAS 13.8.0.4、nvidia-ml-py 13.615.71。

依据 [ORT CUDA 官方说明](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html) 使用 `preload_dlls(directory="")`、GPU extras、禁用 TF32 和分配策略选项。本轮没有安装系统 CUDA Toolkit、改系统 PATH 或驱动。

`scripts/accept_wd_gpu.py` 是显式离线验收工具。先核验模型文件、固定参考图片、变体和 CPU golden 的摘要，再对 1/2/4 批次各执行三轮六图；所有 10,861 个输出概率使用上一阶段同样的 `atol=1e-5, rtol=1e-4`，最终阈值标签和顺序也须一致。输入仍是一张发布者示例及五种格式变体，归属和来源见 [CPU 验收](18-F12-真实模型接入与CPU验收.md)。不是六张独立内容，也不是准确率数据集。

ORT profiling 明确记录 CUDA 节点执行，同时有 CPU 节点；这里的“CUDA”指 CUDA 主执行 provider，不声称整个图所有算子均在 GPU。Runtime 输出的 plugin EP 查询警告保留在日志中，随后实际 CUDA 节点执行、数值与产品记录均已验证。

首轮档案测量（5 ms NVML 采样）及后续复验：

| 请求 batch | 首轮会话显存增量峰值 | 审核后的保守预算 | 首轮暖运行纯推理/图 | 最终复验纯推理/图 |
|---|---:|---:|---:|---:|
| 1 | 2,020,052,992 B（1.88 GiB） | 3 GiB | 0.0887 秒 | 0.0858 秒 |
| 2 | 2,186,477,568 B（2.04 GiB） | 3 GiB | 0.0866 秒 | 0.0831 秒 |
| 4 | 2,876,637,184 B（2.68 GiB） | 4 GiB | 0.0877 秒 | 0.0842 秒 |

预算为观测会话峰值加 25% 和 256 MiB，再向上取整 GiB；运行时按完整会话预算比对剩余显存，不把模型已驻留内存加回可用量，取值偏保守。NVML 是整块显卡采样，会受其它进程和采样间隔影响，因此保留余量和 OOM 处理，不能把它视为显存上限保证。4 图档案也覆盖尾批不足 4 图的调用。

最大概率偏差约 `1.55e-6`，标签全部一致。时延来自同步 `session.run`，包括 ORT CPU/GPU 混合算子，但不包括文件验证、图片解码/预处理、数据库提交和加载。该样例中增大 batch 未显著提高每图速度；保留用户选择，默认 1。模型不同、驱动/依赖变化或其它 GPU 没有匹配档案时，自动退回单图规划。

首轮报告 `.test-tmp/wd-gpu-acceptance-01/report.json` 的精简证据保存在 `tests/fixtures/wd-v3/cuda-rtx5060ti.json`；普通回归检查档案匹配条件和显存余量。原始日志、ORT trace 留在本地，不打入 wheel。

## 产品闭环与使用

真实 GPU HTTP 验收使用 ASGI TestClient，不声称是独立 TCP 服务：导入 6 图，实际批次 4+2，每张标注 provider=cuda；再次执行 6 次当前缓存命中；暂停后提交当前 4 张，恢复只算余下 2 张；取消迟到结果不写标注。人工编辑、审核、导出 6 份 TXT、关闭并重开项目后任务记录均通过。

先退出当前手动启动的服务，避免单实例机制继续复用 CPU 进程，然后运行：

```powershell
./scripts/run.ps1 -Python ./.venv-gpu/Scripts/python.exe serve
```

进入“WD 模型管理”重新校验文件，再在“WD 标注任务”选择自动设备策略与批大小上限。默认 `./scripts/run.ps1 serve` 仍使用原 CPU 环境。启动和任务执行均不自动下载模型/依赖。

新环境需要单独 venv，再执行 `python -m pip install -e ".[wd-gpu]"`；不要与 `[wd-cpu]` 装在同一环境。依赖版本不同不会自动套用本机显存档案。

显式复验命令（输出目录必须不存在）：

```powershell
$env:PYTHONPATH='src'
.venv-gpu/Scripts/python.exe scripts/accept_wd_gpu.py `
  --model-dir "$env:LOCALAPPDATA/StyleLoraAutom/models/wd" `
  --reference-dir .test-tmp/wd-real-evidence `
  --output .test-tmp/wd-gpu-my-check --http-loop
```

`--http-loop` 要求已审核且匹配的本机档案，并断言实际批次为 4+2；其它硬件可以先不加该参数收集测量，但报告不会自行获得信任。
